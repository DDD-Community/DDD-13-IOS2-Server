## A. 잘못 구현된 것 (수정 필요)

### B1·B2. 🔴 투표 후보가 "담긴 후보(pick)"가 아니라 "추천 15개"

**현상**
- `PlaceVoteService.getVoteStatus()` / `submitVote()` 는 `recommendationRepository.findByMeetingIdOrderByRank()`(**추천 15개 전체**)를 투표 후보로 사용.
- 반면 `PlaceConfirmService.confirmPlace()` / `getResult()` 는 `meetingPlacePickRepository`(**담긴 후보**)를 후보로 사용.
- → 투표 화면엔 15개 다 뜨고, 확정은 담긴 것만 계산하는 **불일치**.

**PRD 근거**
- mvp3.md FC-9: "추천된 15개 장소 중 … 실제 투표에 올릴 후보를 각자 '담는' 단계"
- mvp3.md FC-12: "**선정된 후보 장소**를 대상으로 … 투표"
- mvp3-1.md 12-2: "1인 최대 투표 가능 장소 수는 **후보 수**의 50% 이하 (예: 후보 6개 → 최대 3개)"

**파급**
- 최대 투표수 = `recommendations.size()/2` = **7개**(15÷2)로 계산됨. 실제론 담긴 후보 수 기준이어야 함.
- 투표 현황 카드가 담기지 않은 장소까지 노출.

**코드 증거 (grep 확인)**
- `meetingPlacePickRepository` 사용처는 **line 60 단 한 곳**(`existsByMeetingId` boolean 게이트)뿐 — 후보 구성/검증에 미사용.
- `submitVote` line 112-115: `recommendations`(15개) → `candidateCount = recommendations.size()` → `maxVotes = max(1, 15/2) = 7`.
- `getVoteStatus` line 154-155: 후보를 `recommendations`(15개)로 구성.
- `computeAndSaveTravelBurdens` line 229-230: 추천 15개 전부 이동부담 계산.

**수정 방향**
- `getVoteStatus`/`submitVote`의 후보 소스를 `meetingPlacePick`(distinct placeId, 담긴 순서)으로 변경.
- `maxVotes = max(1, pickedCandidateCount / 2)` (담긴 후보 최소 1개 → 최소 1표 보장).
- 이동부담(`travel_burden`) 계산도 담긴 후보 대상으로 한정 (현재 15개 전부 → 불필요 연산).

### B5. 🔴 submitVote의 placeId 후보 검증 전무

**현상**
- `submitVote`(line 117, 123)는 `placeIds.size()`만 검사하고, 각 placeId가 **유효한 후보(담긴 장소/추천)에 속하는지 검증하지 않음**.
- → 임의 placeId, 담기지 않은 장소, 심지어 다른 모임 장소까지 투표로 저장 가능.

**수정 방향**
- `placeIds ⊆ 담긴 후보 placeId 집합` 검증 추가. 위반 시 400.

### M7. 🟠 호스트용 투표 완료/미완료 구성원 현황 (Swagger엔 있고 구현 없음)

**현상**
- `PlaceVoteController.getVoteStatus` Swagger: `"… 모임원 투표완료 현황"` 이라 명시.
- 그러나 `PlaceVoteStatusResponse`는 `totalParticipants`/`votedCount` **집계 숫자만** 반환. per-member 완료여부·호스트 전용 미완료 명단 없음.
- 호스트/구성원 구분 없이 동일 페이로드.

**PRD 근거**
- 12-2 익명성: "호스트에게는 **투표 완료 여부(완료/미완료 구분)만** 공개" (어디 투표했는진 비공개)
- 12-3 미투표 구성원 표시: "**호스트 화면에서만 미완료 구성원 수** 확인. 구성원 화면엔 총 참여율(N/N)만."

**수정 방향**
- 응답에 호출자가 호스트면 구성원별 `{memberId, name, completed}` 리스트(투표 대상 비공개) 또는 미완료 인원/명단 추가. 구성원이면 집계만.

### B3. 🟡 정렬 미구현
- PRD 12-1: 투표 전 **상호명 가나다순**, 투표 후 **득표수 높은순**.
- 현재 `getVoteStatus`는 rank 순(추천 순서) 그대로 반환. 정렬 로직 없음.

### B4. 🟡 후보 최소 개수 가드
- 현재 `startVoting`은 `existsByMeetingId`(≥1)만 검사.
- mvp3-1.md 엣지: "최소 2개 이상 후보 등록 조건, 1개면 투표 시작 비활성화" → **D1 결정 후** 반영.

## B. 누락된 기능 (추가 필요)

### ~~M1. 알림/푸시 시스템~~ / ~~M2. 미응답 리마인드(12-4)~~ — 🚫 MVP 제외 (사용자 결정)
- 푸시 알림(FC-12/13 트리거 7종)·미응답 리마인드 스케줄러 모두 MVP 범위에서 제외.
- 마감 처리 스케줄러(`closeExpiredSessions`)는 알림 없이 상태 전환·확정만 수행(현행 유지).

### M3. 🟠 1~3위 순위 산출 / rank 저장 / 배지 (12-6)
- `confirmPlace`는 **1위만** 선정. 2·3위 rank 산출/저장 없음.
- mvp3-1.md 요구:
  - 좋아요 수 내림차순 1~3위, 동점 처리(이동시간 합 → 환승 합 → 등록순).
  - 1~3위 배지, 후보 < 3이면 후보 수만큼만 노출.
- `getResult`는 candidates를 담긴 순서대로 반환 → rank·정렬·1~3위 제한 없음.
- **수정 방향**: 확정 시 순위 산출 후 저장(또는 결과 조회 시 동일 비교자로 정렬 + rank 부여), 응답에 `rank` 필드 추가.

### M4. 🟡 확정 결과 화면 필드 부족 (13-2)
- 현재 `PlaceResultResponse`: place, confirmedAt, candidates(place/voteCount/totalSeconds/totalTransfers).
- 누락:
  - **순위 배지(rank)** — M3
  - **구성원 확인 상태** ('참석 예정' / '확인 전') — 엔티티·API 전무
  - **예약 가능 시 '예약 사이트로 이동' CTA** — Place에 예약 링크 필드 없음
  - **영업시간 / 분위기 태그 / 썸네일** — 데이터소스 확인 필요(아래 데이터 갭)
  - **구성원별 환승·이동시간 리스트** (확정 장소 기준)

### M5. 🟡 장소 상세 "친구들 거리보기" 바텀시트 (12-1.1)
- 구성원별 출발지→장소 경로(점선), 프로필 말풍선('환승 N회 N시간 N분'), 나/팀원 구분, 최장 이동자 빨강 강조.
- 현재 `PlaceDetailResponse`엔 이동부담 정보 없음. `getVoteStatus`엔 burden 있으나 **구성원 식별·출발지·프로필 미포함**(memberId만).
- **함께 담기 N**(담은 모임원 수)은 FC-9 카드엔 있으나(`pickCount`) 상세 응답엔 정리 필요.

### M6. 🟡 투표 중 엣지 처리
- "투표 시작 후 후보 추가 불가" — `PlacePickService`의 담기 API가 VOTING 상태에서 차단되는지 검증 필요.
- "투표 시작 후 합류자 기권, 전체 인원 투표 시작 시점 고정" — `isAllVotedInternal`이 **live** `meetingParticipant`를 사용. 투표 시작 시점 스냅샷 기준인지 검증 필요(신규 합류 시 분모 변동 위험).

### 데이터 갭 (place 마스터)
- `Place` 도메인: **영업시간 없음**, **지번주소 없음**(단일 `address`만), **썸네일 없음**, **예약 링크 없음**.
- Place는 외부 파이프라인 적재 read-only → PRD의 영업시간/지번/복사아이콘/썸네일은 **데이터 소스 확보 여부에 종속**. 확인 필요.
