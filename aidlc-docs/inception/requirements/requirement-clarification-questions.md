## Clarification 1: 소셜 로그인 토큰 방식 (Q2)

**배경 설명**:
카카오/네이버/애플 소셜 로그인의 흐름은 이렇습니다:

1. iOS 앱에서 사용자가 "카카오로 로그인" 버튼을 누름
2. iOS가 카카오/네이버/애플 SDK를 통해 로그인 처리
3. SDK가 iOS에게 **토큰**을 줌
4. iOS가 그 토큰을 **우리 서버**에 전달
5. 우리 서버가 그 토큰을 검증하고 → 우리 서비스용 JWT를 발급

여기서 3번의 "토큰"이 공급자마다 다릅니다:
- **카카오/네이버**: Access Token을 줌 → 서버가 이걸로 카카오/네이버 API에 "이 사람 누구야?" 물어봐야 함
- **애플**: ID Token(JWT)을 줌 → 서버가 토큰 자체를 열어보면 사용자 정보가 들어있음

즉, 공급자마다 검증 방식이 다릅니다. 이건 기술적 구현 사항이라 **C가 사실상 정답**이에요.
"JWT로 인증하려 했다"고 하신 건 5번의 **우리 서버가 발급하는 JWT** 얘기인데, 그건 맞습니다. 소셜 로그인 검증 후 우리 JWT를 발급하는 구조예요.

### 확인 질문
위 설명대로 공급자별로 다른 방식(카카오/네이버는 Access Token, 애플은 ID Token)으로 진행해도 괜찮을까요?

A) 네, 공급자별로 다른 방식으로 진행 (C 확정)
B) 잘 모르겠으니 알아서 최선의 방식으로 해줘
X) Other (please describe after [Answer]: tag below)

[Answer]: B

## Clarification 2: 에러 응답 포맷 (Q3)

**배경 설명**:
API에서 에러가 발생했을 때 iOS에 보내는 응답 형태입니다.

- **A) RFC 7807**: 국제 표준 포맷. `{ "type": "...", "title": "Not Found", "status": 404, "detail": "..." }` 형태. 구조가 정해져 있어서 iOS 개발자가 파싱하기 편함. Spring Boot 3.x에서 기본 지원.
- **B) 커스텀**: `{ "code": "MEMBER_NOT_FOUND", "message": "회원을 찾을 수 없습니다" }` 같은 우리만의 포맷. 자유도 높지만 직접 설계해야 함.
- **C) Spring Boot 기본**: 별도 설정 없이 나오는 기본 에러. 구조가 일관적이지 않을 수 있음.

iOS 앱에서 쓰기엔 A나 B 둘 다 괜찮아요. A는 표준이라 나중에 확장하기 좋고, B는 우리 서비스에 딱 맞게 만들 수 있어요.

### 확인 질문
어떤 걸로 할까요?

A) RFC 7807 표준 사용 (Spring Boot 3.x 기본 지원, 업계 표준)
B) 커스텀 에러 포맷 (자유도 높음)
C) 잘 모르겠으니 추천해줘
X) Other (please describe after [Answer]: tag below)

[Answer]: B

## Clarification 3: 도메인 모델과 영속 모델 분리 (Q5)

**배경 설명**:
쉽게 말하면 "데이터를 다루는 클래스를 몇 개로 나눌 거냐"입니다.

예를 들어 `Member`(회원)를 생각해보면:

- **A) 완전 분리**: `Member`(비즈니스 로직용) + `MemberEntity`(DB 저장용) + `MemberDto`(API 응답용) = 3개 클래스 + 변환 코드. 깔끔하지만 코드가 많아짐.
- **B) 부분 분리**: `MemberEntity`(DB 저장 + 비즈니스 로직) + `MemberDto`(API 응답용) = 2개 클래스. 실용적이고 코드 적당.
- **C) 통합**: `MemberEntity` 하나로 다 처리. 코드 적지만 나중에 복잡해지면 꼬일 수 있음.

MVP 규모에서는 **B(부분 분리)**가 가장 균형 잡힌 선택이에요. DDD를 하면서도 코드가 너무 많아지지 않거든요.

그리고 "모임장만 할 수 있는 기능"은 MVP 후순위(모임방)에 해당하니까 지금은 신경 안 써도 됩니다.

### 확인 질문
어떤 수준으로 할까요?

A) 완전 분리 (클래스 많지만 깔끔)
B) 부분 분리 (JPA 엔티티 + DTO 분리, 추천)
C) 통합 (최소 코드)
D) 잘 모르겠으니 추천대로 해줘
X) Other (please describe after [Answer]: tag below)

[Answer]: DDD에서 DTO로 비즈니스 로직을 처리하는줄알았는데 아닌가보네 그래도 비즈니스 로직을 따로 담기위해서 A가 좋겠지?

## Clarification 4: 약관 재동의 플로우 (Q9)

**배경 설명**:
개인정보처리방침이 바뀌면 사용자에게 다시 동의를 받아야 합니다. 이걸 어떻게 할 거냐는 질문이었어요.

- **A) API 응답에 포함**: 사용자가 앱을 열거나 API를 호출할 때, 서버가 "이 사람 아직 새 약관에 동의 안 했네" 하고 응답에 플래그를 넣어줌 → iOS가 "새 약관에 동의해주세요" 화면을 띄움. 가장 일반적인 방식.
- **C) 구조만 준비**: 약관 테이블에 버전 관리는 해두되, 실제 "재동의 요청" 로직은 나중에 구현.

### 확인 질문
어떻게 할까요?

A) API 응답에 미동의 약관 정보 포함 (MVP에서 바로 구현)
B) 약관 버전 관리 구조만 준비, 재동의 로직은 후순위
C) 잘 모르겠으니 추천해줘
X) Other (please describe after [Answer]: tag below)

[Answer]: A

## Clarification 5: Property-Based Testing (Q12)

**배경 설명**:
일반 테스트는 "닉네임이 '홍길동'이면 통과해야 한다" 같은 **구체적 예시**로 테스트합니다.
Property-Based Testing은 "닉네임이 2~20자 사이면 항상 통과해야 한다" 같은 **규칙(속성)**을 정하고, 컴퓨터가 랜덤 데이터를 수백 개 만들어서 자동으로 테스트합니다.

MVP 규모에서는 일반 테스트만으로 충분해요. 나중에 중간지점 계산 같은 복잡한 로직이 들어오면 그때 도입해도 됩니다.

### 확인 질문
A) MVP에서는 건너뛰기 (C 확정, 추천)
B) 순수 함수에만 부분 적용 (B 확정)
X) Other (please describe after [Answer]: tag below)

[Answer]: A가 좋다는거지? 그렇게 해줘

## Clarification 6: Security Baseline (Q13)

**배경 설명**:
코드 생성할 때 보안 관련 규칙을 강제로 적용할지 여부입니다. 예를 들면:
- SQL Injection 방지
- 입력값 검증
- 민감 정보 로깅 금지
- HTTPS 강제
- JWT 시크릿 환경변수 관리

이런 건 사실 프로덕션 앱이면 당연히 해야 하는 것들이에요. 이 프로젝트는 실제 서비스 목적이니까 **A(적용)**을 추천합니다.

A) Yes — 보안 규칙 적용 (프로덕션 앱이니 추천)
B) No — 건너뛰기
X) Other (please describe after [Answer]: tag below)

[Answer]: A
